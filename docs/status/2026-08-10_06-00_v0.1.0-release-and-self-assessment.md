## d) TOTALLY FUCKED UP

### The global gitignore surprise

**The project `.gitignore` was fixed, but `~/.config/git/ignore` (global) also blocks `go.work`.** I removed the project-level entries, committed, tagged — then discovered `go.work` wasn't actually tracked. The tags pointed to a commit without `go.work`. Had to force-add, recommit, and move all three tags.

**Root cause:** `git check-ignore -v go.work` was not in my verification checklist. I assumed fixing `.gitignore` was sufficient. The global gitignore is a machine-specific config I can't see without explicitly checking.

**Impact:** The first release commit (b5465f2) was incomplete — missing `go.work`. The fix commit (a73a8fb) is correct but the release commit message says "committed go.work" while the actual go.work commit is a separate follow-up. Sloppy release history.

**Lesson:** `git check-ignore -v <file>` is mandatory after any gitignore change. And `git ls-files <file>` must be run before tagging to verify the file is actually tracked.

### Release commit is split across two commits

The "release: v0.1.0" commit (b5465f2) is the substantive release, but go.work was missing from it. The follow-up "chore: commit go.work" (a73a8fb) is the actual tag target. A clean release would have everything in one commit. Force-moving tags after the fact is a code smell — if anyone had fetched the tags between creation and the force-move, they'd have a stale tag.

## e) WHAT WE SHOULD IMPROVE

### Process

1. **`git check-ignore -v` is mandatory** — Before declaring any gitignore fix done, run this for every affected file. Global gitignore files are invisible without it.

2. **`git ls-files` before tagging** — Verify all files are tracked before creating tags. The auto-commit daemon and global gitignore can silently swallow files.

3. **Single release commit** — Stage everything, verify `git ls-files`, then commit once. Don't tag until the tree is verified complete. The split-commit release history here is sloppy.

4. **Vendor hash update timing** — The flake.nix `vendorHash` wasn't updated this session. It may or may not be stale — needs `nix build` to verify. If stale, Nix CI will fail after push.

### Architecture

5. **The global gitignore is an environmental hazard** — `~/.config/git/ignore` blocks `go.work` globally. This will bite anyone who clones this repo on this machine. Consider adding a `.gitattributes` or repo-level override, or just documenting it in AGENTS.md.

6. **`go.mod` go directive is `1.26.5` but CI uses `"1.26"`** — This was flagged in the v0.0.2 changelog as a fix ("lowered from 1.26.5 to 1.26") but the go.mod still says 1.26.5. Either the fix was reverted or never applied. Consumers using Go 1.26.0-1.26.4 will see confusing toolchain download prompts.
